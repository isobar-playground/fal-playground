# Maszynka Video media processing stays serverless: crops in the browser, concatenation via FAL ffmpeg

The Maszynka Video pipeline needs two capabilities the repo does not have: cutting panels out of a generated grid image, and concatenating per-scene clips into one final video. The app runs on serverless hosting (Neon + Next.js API routes), so shipping an ffmpeg binary on our own backend is the most expensive option and was rejected.

**Cropping happens client-side** with the native Canvas API: panels are cut at equal fractions of the layout declared in `gridGenerationPayload`, and each cut line is snapped to a detected gutter (1D gradient projection over `ImageData`) within a ±5% window around the expected position. FAL has no deterministic crop API (`workflowutils/crop` does not exist; smart-resize regenerates the image; SAM-3 is non-deterministic segmentation), and sharp — while officially supported on Vercel — only cuts at given coordinates, it detects nothing, so a server route would add a dependency and a route without solving gutter drift. `v3.fal.media` serves `access-control-allow-origin: *` (verified 2026-08-07), so the browser can legally read FAL-hosted grids. Escape hatches: crop previews before animation and the spec-mandated Replace crop. Upgrade path if browser cropping proves unreliable: sharp on a Vercel route, same fraction+snap math.

**Clip concatenation goes through FAL's ffmpeg endpoint**: the ordered clip URLs are submitted with the operator's existing BYOK FAL key and the hosted result URL becomes `finalVideoUrl` directly. Alternatives rejected: ffmpeg.wasm (~30 MB dependency, and the joined file would still need an upload to get a URL) and server-side ffmpeg (binary size/runtime limits on serverless). Consequence accepted: joining costs FAL credits and requires their ffmpeg endpoint to stay available; the exact endpoint id is verified at build time.
